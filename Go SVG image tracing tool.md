# Build the Go tracer permissive, VTracer-style

Write the tracing core yourself in pure Go, model it on VTracer's linear pipeline plus Schneider curve fitting, and keep every line of Potrace-derived code out of it. That is the one combination that leaves all three distribution routes (downloadable CLI, server API, browser WebAssembly) open under any licence you choose. No maintained, permissively licensed, colour-capable tracer exists in pure Go today: the only real engines are GPL machine translations of Potrace last touched in July 2023, so "pure Go, permissive, colour, single static binary" is an empty niche ([gotranspile/gotrace](https://github.com/gotranspile/gotrace)). For black-and-white work the Potrace algorithm remains the quality reference, and for colour the VTracer design is the strongest open template; ML vectorisers are not practical inside a self-hosted Go tool as of November 2026. GPL code is harmless on your own server but becomes a source-disclosure obligation the moment you ship a binary or a WASM module, which is exactly the roadmap described ([FSF GPL FAQ](https://www.gnu.org/licenses/gpl-faq)). The recommended shape is one library with a single `Options` struct behind three thin entry points (`cmd/` CLI, server, wasm), shipped in phases: bilevel first, colour second, size and quality third, online fourth. Three things need outside confirmation before you rely on them: a lawyer's view on the clean-room and WASM questions, a direct re-read of several LICENSE files, and your own measurements of Go-WASM speed, because no trustworthy published numbers exist.

## Two pipelines cover the field: Potrace for bilevel, VTracer for colour

Every classical tracer does the same four jobs: reduce the image to a small set of flat regions, walk each region's boundary, simplify that boundary, and fit curves. The tools differ in how carefully they do the last two, and that decides which is best for which input.

**Potrace** is bilevel-only. It walks boundaries along pixel edges, finds the polygon with the fewest segments under a half-pixel "straightness" constraint by dynamic programming, nudges vertices to sub-pixel positions, classifies each vertex as corner or curve with a single scalar (`alphamax`, default 1), and optionally merges adjacent Béziers under `opttolerance` (default 0.2) ([potrace(1)](https://www.mankier.com/1/potrace); [arXiv 2306.09039](https://arxiv.org/pdf/2306.09039)). Its fitting stages are worst-case quadratic, though its own source comments call them near-linear in practice ([trace.c](https://lxr.kde.org/source/graphics/glaxnimate/external/potrace/src/trace.c)). It has no colour support and no centerline mode, and its author says that is unlikely to change ([Potrace FAQ](https://potrace.sourceforge.net/faq.html)). The last release is **1.16 from 17 September 2019** ([potrace.sourceforge.net](https://potrace.sourceforge.net/)).

**VTracer** (Rust) handles colour end to end: hierarchical colour clustering, pixel-edge path walking, staircase removal, a greedy penalty-limited polygon simplifier, corner-preserving subdivision smoothing, splice-point detection, then one least-squares cubic per run ([simplify.rs](https://docs.rs/crate/visioncortex/0.8.0/source/src/path/simplify.rs); [smooth.rs](https://docs.rs/crate/visioncortex/0.8.0/source/src/path/smooth.rs)). Every stage is a single linear pass with no matrix larger than 2x2, which is why it ports cleanly to Go. It is also the project that is moving: a ground-up 1.0 rewrite reached **alpha.4 on 29 August 2026**, adding a seam-free cutout mode, watershed segmentation, OKLab palette matching, adaptive thresholding and a `--simplify` pass that "typically halves file size" ([vtracer README](https://cdn.jsdelivr.net/gh/visioncortex/vtracer@master/README.md); [crates.io](https://crates.io/api/v1/crates/vtracer)). Those additions show where the older pipeline was weakest (node count, colour selection, seams), so design for them from day one.

**ImageTracer.js** is the easiest to port and the weakest fitter. It quantises with a k-means variant, extracts per-colour layers with a marching-squares variant, and fits only lines and quadratic splines; its author lists the split-point choice as "a guess" and recommends borrowing from Potrace ([process overview](https://cdn.jsdelivr.net/npm/imagetracerjs-g@1.2.6-fix/process_overview.md)). **AutoTrace** fits cubic splines with explicit corner detection and iterative least squares, and is the only open tool with centerline tracing, but a 2004 field report shows defaults producing about 557,000 splines on a line drawing before tuning cut that to 731 ([autotrace(1)](https://mankier.com/1/autotrace); [linux.com](https://www.linux.com/?p=515650)).

| Approach | Input | Fitting | Strength | Weakness | Code licence |
|---|---|---|---|---|---|
| Potrace | Bilevel only | Optimal polygon (DP), alpha corner test, Bézier merge | Cleanest curves on line art and logos | No colour, no centerline, frozen since 2019 | GPL-2.0-or-later |
| VTracer | Colour and bilevel | Linear: staircase removal, greedy simplify, subdivision, one cubic per run | Colour, speed, very large images, active | More parameters to tune; slightly rounder corners (inference) | MIT / Apache-2.0 |
| ImageTracer.js | Colour | Lines and quadratics, recursive split | Simple, public domain | Heuristic fitter, dormant | Unlicense |
| AutoTrace | Colour, centerline | Corner detection + iterative cubic least squares | Only centerline option | Very large output | GPL (program) / LGPL (library) |

### Which is best

**For black-and-white, use a Potrace-style fitter; for colour, use a VTracer-style pipeline with stacked layers.** The colour half of that verdict has published support. In the StarVector benchmark VTracer scored DinoScore 0.954 at 9.7k tokens against AutoTrace's 0.942 at 59.1k, so comparable fidelity at about one-sixth the size, and ran at 0.09 s per image ([StarVector](https://arxiv.org/html/2312.11556v3)). A CVPR 2026 paper called VTracer "the most usable open-source option" and research systems such as LayerTracer use it as their geometry back end ([VectorArk supplemental](https://openaccess.thecvf.com/content/CVPR2026/supplemental/Gehlaut_VectorArk_Learning_Practical_CVPR_2026_supplemental.pdf); [LayerTracer](https://arxiv.org/html/2502.01105v3)).

The black-and-white half rests on reputation and algorithm design, not on a benchmark. **No head-to-head study of Potrace against VTracer or AutoTrace on bilevel images was found.** Potrace's low scores in the StarVector table reflect a colour test set fed to a bilevel tool, and that table's "10 s per image" for Potrace is anomalous for a fast C program and should not be quoted as its speed. Token counts for the same tool also differ five-fold between papers, so only within-table comparisons mean anything. Build your own benchmark early (see the build plan) and let it settle the question.

### The component choices underneath

**Contour extraction: follow pixel edges ("cracks"), not pixel centres.** Potrace and VTracer both do this. Paths run between pixels, so neighbouring colour regions share an identical integer boundary and holes fall out of orientation or of Potrace's invert-and-rescan trick. Pixel-centre followers such as Moore tracing lose half a pixel, and marching squares yields unordered segments and suits only a sub-pixel mode driven by anti-aliased values ([Wikipedia: Boundary tracing](https://en.wikipedia.org/wiki/Boundary_tracing)). The 2x2 checkerboard ambiguity is unavoidable; Potrace resolves it with an explicit turn policy, defaulting to "minority" ([potrace(1)](https://man.archlinux.org/man/potrace.1.en.raw)).

**Simplification: remove staircases before any generic simplifier.** Running Ramer-Douglas-Peucker or Visvalingam-Whyatt on a raw pixel staircase either keeps the stairs or erodes real corners (the researchers' analysis, not a cited result). When a generic simplifier is needed, Visvalingam-Whyatt gives more uniform results and avoids RDP's sawtooth artefacts ([richoncode](https://richoncode.github.io/webartests/learning-vectorization/visvalingam-whyatt)).

**Curve fitting: Schneider's 1990 Graphics Gems algorithm is the general-purpose workhorse.** It fixes end tangents, solves a 2x2 least-squares system for two handle lengths, reparameterises with Newton steps, and splits at the worst point ([fitcurves.c](https://mirrors.sunsite.dk/blender/source/chest/neogeo/traces/fitcurves.c)). Inkscape's lib2geom carries the same algorithm, and VTracer 1.0's simplifier descends from it via paper.js ([lib2geom](https://grok.dragonflybsd.org/xref/dports/math/lib2geom/lib2geom-1.1/src/2geom/bezier-utils.cpp)). The robust recipe is to detect corners first, then fit each corner-to-corner run. Tangents estimated from two pixel points are noisy, so estimate them over several points as AutoTrace does.

**Colour quantisation: Wu's quantizer refined by k-means.** Celebi's comparison of quantizers found k-means initialised with Wu's method the best overall; on the Baboon image at 32 colours it cut error from 546.0 (median cut) to 329.6 ([Celebi, arXiv 1101.0395](https://www.arxiv.org/pdf/1101.0395)). Avoid NeuQuant, which one engineering comparison found non-deterministic and far worse on gradients ([pgs-release notes](https://connollydavid.github.io/pgs-release/quantizers)). Working in OKLab follows VTracer 1.0's choice; **no study measures quantizer or colour space by final vector quality**, so treat OKLab as a sensible default to verify. Palette quality alone is not enough either: anti-aliased edges quantise into thin intermediate bands that become sliver shapes, so region-level merging of small clusters and speckle filtering matter as much. Input noise matters too: one review saw VTracer emit 81 paths for a clean PNG and 720 for a low-quality JPEG of similar content ([arXiv 2306.06441](https://arxiv.org/pdf/2306.06441)).

**Layering: stack by default.** Stacked output lets each shape extend beneath the ones above, avoids holes and yields fewer shapes; independently fitted cut-out shapes showed seams in VTracer 0.x until 1.0 replaced them with a shared-boundary tessellation ([vtracer README, 2024 snapshot](https://cdn.jsdelivr.net/npm/svgit4me@1.0.7/vtracer-webapp.2024.5/README.md)). Abutting anti-aliased shapes show hairline gaps in browsers, and the documented fixes are all compromises ([Stack Overflow 47451435](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/47451435/svg-prevent-transparent-gaps-between-adjacent-polygons)).

**ML: not for this tool.** Optimisation methods are slow: LIVE took 33 s to 7,150 s per image on an RTX 3090 Ti ([arXiv 2306.06441](https://arxiv.org/pdf/2306.06441)). LLM generators need 1B to 8B-parameter models, average 41 to 74 s per sample, and hit context limits on complex images; OmniSVG "fails on natural images" ([StarVector](https://arxiv.org/html/2312.11556v3); [OmniSVG](https://arxiv.org/pdf/2504.06263)). Classical tracing takes under 1 s at 1024x1024. The ideas worth borrowing without any ML come from the commercial leader's own feature list: shared-boundary graphs, whole-shape fitting of circles and rectangles, and sub-pixel boundaries from anti-aliasing values ([vectorizer.ai](https://vectorizer.ai/); vendor claims, not independently verified).

## Pure-Go, permissive, colour tracing is an unoccupied niche

A GitHub search on 9 November 2026 found exactly two Go Potrace engines, and nothing for ImageTracer, AutoTrace or contour tracing in Go. Coverage was GitHub-only, so packages on other hosts could have been missed.

| Go package | What it is | Licence | State | Verdict |
|---|---|---|---|---|
| [dennwc/gotrace](https://github.com/dennwc/gotrace) | Potrace port + cgo bindings | GPL-2.0 | Archived, marked deprecated | Do not use |
| [gotranspile/gotrace](https://github.com/gotranspile/gotrace) | cxgo machine translation of Potrace, with CLI | GPL-2.0 | 28 stars, last push 2023-07-26 | Black-box reference only |
| [nyorotan/vectrace](https://github.com/nyorotan/vectrace) | gotrace-based, adds colour layers | GPL-2.0 | 1 star; indexed input only; not importable | Do not use |
| [yclw/go-vtracer](https://github.com/yclw/go-vtracer) | cgo binding to VTracer | MIT | 5 stars; links prebuilt shared libraries | Do not use |
| [fogleman/primitive](https://github.com/fogleman/primitive) | Shape-by-shape hill climbing | MIT | 13.6k stars | Not a tracer |

The transpiled gotrace is the most complete monochrome option, but it is non-idiomatic C-in-Go, depends on the cxgo runtime library, and pins no exact upstream Potrace version in its config ([go.mod](https://raw.githubusercontent.com/gotranspile/gotrace/main/go.mod); [cxgo.yml](https://raw.githubusercontent.com/gotranspile/gotrace/main/cxgo.yml)). The VTracer binding links `.so`/`.dylib`/`.dll` files via rpath, which defeats static binaries and cross-compilation, and exposes only the pre-1.0 option set ([vtracer.go](https://raw.githubusercontent.com/yclw/go-vtracer/main/vtracer.go)).

### What to reuse and what to write

**Write the whole tracing core in-tree.** Each piece is small, and the available Go implementations are tiny hobby repositories, several with no licence file, which means all rights reserved and not copyable.

| Component | Decision | Reason |
|---|---|---|
| Decoding PNG/JPEG/GIF | Standard library | Already there |
| BMP/TIFF/WebP decoding | [golang.org/x/image](https://github.com/golang/image), optional | BSD-3, Go-team maintained; each extra format widens attack surface |
| Pixel-edge contour tracing with holes | Write | No reusable Go implementation exists |
| Staircase removal, RDP, Visvalingam-Whyatt | Write | Roughly 50 to 100 lines each (researchers' estimate) |
| Schneider cubic fitting | Write, from the Graphics Gems lineage | Only zero-star Go repos exist; [JohnForster/fitcurves](https://github.com/JohnForster/fitcurves) (MIT) is a cross-check |
| Colour quantisation in OKLab | Write | Go quantizers are small, stale and sRGB-only; [go-quantize](https://github.com/ericpauley/go-quantize) (BSD-3) is a median-cut reference |
| Colour-space maths | Inline, or [go-colorful](https://github.com/lucasb-eyer/go-colorful) | MIT, maintained; the OKLab transform is short |
| SVG writer | Write | A tracer emits only `<path>` elements; [ajstarks/svgo](https://raw.githubusercontent.com/ajstarks/svgo/master/LICENSE) is CC-BY-4.0, an awkward licence for code |
| PDF/EPS export, boolean ops | [tdewolff/canvas](https://github.com/tdewolff/canvas), later and outside the core | MIT, active, but its author warns of bugs and API churn |
| Shared-boundary planar map for seam-free cutout | Write | No Go library provides it; the most novel engineering item |
| CLI flags | Standard `flag`, or [kong](https://github.com/alecthomas/kong) | A single-command tool does not need cobra |

Avoid cgo image libraries (libvips, ImageMagick, OpenCV bindings) entirely: they break the single static binary and the WASM build. Use VTracer's flag vocabulary (`--preset`, `--mode`, `--filter-speckle`, `--color-precision`, `--path-precision`, `--max-colors`) where the meaning matches, so existing users and scripts transfer.

The market context supports the effort. Vectorizer.AI charges US$9.99 a month for web use and $0.05 to $0.20 per image by API, and Vector Magic charges $9.95 a month or $295 for desktop; both let you preview free and pay to download ([vectorizer.ai pricing](https://vectorizer.ai/pricing); [vectormagic.com pricing](https://vectormagic.com/pricing)). The feature set users expect follows from those tools: a zero-config automatic mode, named presets, colour count or fixed palette, speckle removal, one simplify knob, stacked versus cutout, and a before/after view.

## GPL Potrace code forecloses closed CLI and WASM builds; the algorithm itself is free

This section is research, not legal advice. Items marked **[LAWYER]** need professional confirmation before you depend on them.

Potrace is licensed GPL "version 2, or (at your option) any later version", and its author sells a non-GPL "Potrace Professional" through Icosasoft for proprietary integration; price and terms are not public ([potrace.sourceforge.net](https://potrace.sourceforge.net/)). The Go ports inherit that. The FSF's position is explicit: "translation of a work is considered a kind of modification", and a program that links a GPL library falls under the GPL as a whole ([FSF GPL FAQ](https://www.gnu.org/licenses/gpl-faq)). Go links statically, so importing gotrace makes your binary a GPL work with no dynamic-linking grey area to argue **[LAWYER]**. Every Potrace port found, in JavaScript, Python, Go and WASM, labels itself GPL, so claiming otherwise would put you out of step with both community practice and a copyright holder who actively sells licences.

What the GPL requires depends on how the software reaches users:

| Distribution route | With Potrace-derived GPL code | With own, MIT/Apache or Unlicense code |
|---|---|---|
| Downloadable CLI binary | Distribution: the whole binary is GPL and complete source must be offered. Closed source needs Potrace Professional. | Open or closed, your choice. Ship third-party notices. |
| Server-side API | Not distribution under GPLv2/v3 per the FSF; no source duty, even if modified. Handing the binary to a customer or an on-premises install is distribution. | No obligations beyond notices on distributed copies. |
| WASM sent to browsers | Distribution: the FSF says programs "distributed to the user when they visit the web site" must have source released under the GPL. | Allowed. Link a licences file from the page. |

The server exemption is the FSF's own reading ("The GPL permits anyone to make a modified version and use it without ever distributing it to others"), and it is the difference between GPL and AGPL ([FSF GPL FAQ](https://www.gnu.org/licenses/gpl-faq)). WebAssembly is not named in the FAQ; the "other languages are used as well" wording makes it very likely to count as conveying object code, and no case law on WASM delivery was found **[LAWYER]**. Existing Potrace WASM builds label themselves "GPL-v2.0, due to the original Potrace license" ([esm-potrace-wasm](https://unpkg.com/esm-potrace-wasm@0.4.1/README.md)). In every scenario the SVG a user produces is unaffected, since copyright in a program does not reach its output.

The permissive alternatives are real. VTracer is MIT on GitHub and "MIT OR Apache-2.0" in its crate metadata; the core visioncortex library shows Apache-2.0 on GitHub and "MIT OR Apache-2.0" on crates.io ([github.com/visioncortex](https://github.com/visioncortex); [crates.io](https://crates.io/api/v1/crates/visioncortex)). That discrepancy is unresolved because the LICENSE files were not read directly, but either reading is permissive: you may study and even translate the code into Go, keeping the copyright notice and licence text for translated portions. ImageTracer.js is public domain under the Unlicense ([imagetracerjs README](https://unpkg.com/imagetracerjs@1.2.6/README.md)). Schneider's Graphics Gems code may be used "in any program, product, or library, non-commercial or commercial" ([SPDX: Graphics-Gems](https://spdx.org/licenses/Graphics-Gems)). AutoTrace's LGPL library is effectively copyleft for a statically linked Go project.

### Reimplementing Potrace from the paper

Copyright protects expression, not methods: US law excludes "any idea, procedure, process, system, method of operation" from protection ([17 U.S.C. §102](https://www.govinfo.gov/content/pkg/USCODE-2024-title17/html/USCODE-2024-title17-chap1-sec102.htm)), and Indian commentary describes the same idea-expression line drawn through case law ([IP & Legal Filings](https://ipandlegalfilings.com/the-relevance-of-idea-expression-dichotomy-under-copyright-law-in-the-context-of-computer-programs)). Selinger publishes the algorithm as a standalone technical paper, separate from the code ([potrace.sourceforge.net](https://potrace.sourceforge.net/)). An implementation written from that paper, without reading or translating the GPL source, is not a derivative of the code and can carry any licence **[LAWYER]**, for India and for each target market.

Defensibility depends on process, and three cautions follow from that.

First, **the Potrace stage descriptions in this project's research notes were reconstructed from the GPL C source**, because the paper could not be fetched. Anyone writing a clean-room Potrace-style fitter should work from [potrace.pdf](https://potrace.sourceforge.net/potrace.pdf) itself and not from those notes. The high-level description in this report stays at the level of ideas.

Second, **do not ask an AI assistant to translate Potrace to Go or prompt it with Potrace source.** One commentator notes there is "zero legal precedent" that an LLM-assisted rewrite avoids being a derivative work ([LWN comment](https://lwn.net/Articles/1061957); a reader comment, not legal authority). Review any generated code for resemblance to Potrace's structure and identifiers **[LAWYER]**.

Third, keep a paper trail: design notes citing paper sections, your own naming and data structures, and a README statement that the code is an independent implementation. Testing against the Potrace binary's output as a black box is safe. Do not use "Potrace" as a product name: it is the author's trademark, and ports may use it only with permission ([Potrace README](https://lxr.kde.org/source/graphics/glaxnimate/external/potrace/README)) **[LAWYER]**.

On patents, no source consulted mentions one on Potrace, Schneider's fitting or VTracer. That is an absence of evidence, not a freedom-to-operate opinion, and no patent search was done **[LAWYER]**. The researchers' understanding that India's Patents Act excludes algorithms and computer programs "per se" was not verified against a primary source.

### Licence for your own code

MIT or Apache-2.0 both keep closed-source binaries, SaaS, WASM and later dual licensing available. Apache-2.0 adds an explicit patent grant, which is useful if you accept outside contributions. The one trap is GPL: the FSF has "never considered the Apache License to be compatible with GPL version 2" ([Apache: GPL compatibility](https://www.apache.org/licenses/GPL-compatibility)). If you ever want an optional Potrace-backed mode, isolate it as a separate executable invoked as a subprocess, never linked. Add a contributor agreement or DCO from the start if you want to preserve relicensing freedom. Before release, confirm every dependency's licence against its actual LICENSE file; most licences in this research come from GitHub's auto-detection.

## One Options struct behind three thin entry points

The official Go layout guidance describes the needed shape directly: the importable package at the module root, commands under `cmd/`, and everything else under `internal/`, which the Go team recommends using "as much as possible" ([go.dev module layout](https://go.dev/doc/modules/layout)). For this project that means a root tracer package, `internal/` packages for quantise, segment, contour, fit and SVG writing, and three mains: `cmd/<tool>`, `cmd/<tool>-server` and `cmd/<tool>-wasm`. Separate mains keep `net/http` and `syscall/js` out of the library's import graph, which matters for WASM size.

The pipeline runs in seven stages: decode, normalise to a flat pixel buffer, pre-process (optional resize, blur, threshold or quantise in OKLab), segment into a label map with speckle merging, trace pixel-edge contours with hole hierarchy, simplify and fit curves, then write SVG. Copy VTracer's split between an expensive, cacheable `segment` step and a cheap re-runnable `finish` step, so a web UI can re-fit curves when only a smoothing slider moves ([vtracer README](https://cdn.jsdelivr.net/gh/visioncortex/vtracer@master/README.md)). Offer three entry levels mirroring VTracer's bindings: reader-to-writer, already-decoded image, and raw RGBA with width and height. One exported `Options` struct with presets should back CLI flags, HTTP parameters and the JavaScript options object through a single validation function, so presets behave identically everywhere. The struct-over-functional-options preference and `context.Context` cancellation are community convention, not official guidance.

For SVG output, round coordinates aggressively (Potrace defaults to one-tenth of a pixel) and emit compact path data directly instead of depending on a post-processor ([potrace(1)](https://www.mankier.com/1/potrace)). The compactness techniques (relative commands, `h`/`v` shorthands, one path per colour where stacking allows) are the researchers' recommendations; their size effect on traced output is unmeasured.

For the CLI, follow Potrace's conventions: positional inputs, `-` for stdin and stdout, one output per input with the suffix swapped, and exit codes 0 for success, 1 for usage errors and 2 for anything else ([potrace(1)](https://www.mankier.com/1/potrace)). Pure Go cross-compiles without a C toolchain, which is the practical payoff of the no-cgo rule.

### WebAssembly: ship standard Go first, measure, then consider TinyGo

Standard Go targets the browser with `GOOS=js GOARCH=wasm`. A minimal demo measured in May 2026 was **2.5 MB raw and 758 KB gzipped** on Go 1.26.3 against **702 KB raw and 239 KB gzipped** on TinyGo ([kmcd.dev](https://kmcd.dev/posts/wasm-demos/)). The Go wiki puts the standard floor at about 2 MB and warns that imports commonly push it past 10 MB ([Go Wiki: WebAssembly](https://go.dev/wiki/WebAssembly)). TinyGo's support page lists `image`, `image/png` and `image/jpeg` as passing tests, but `fmt`, `strconv`, `bytes` and `sort` as importable with tests not all passing, and those results are for linux/amd64, not wasm ([TinyGo stdlib support](https://tinygo.org/lang-support/stdlib)). So write the library to be TinyGo-friendly (little reflection, no `encoding/json` or `fmt` in hot paths) and run your own test suite under TinyGo before trusting it.

Three design consequences follow. Go's WASM has no parallelism, so the browser build gains nothing from goroutine fan-out and must run inside a Web Worker to keep the page responsive ([Go blog: wasmexport](https://go.dev/blog/wasmexport)). Letting the browser decode the image and passing raw RGBA into Go drops the decoders from the binary. And **no trustworthy benchmark of Go-compiled WASM against native Go for image workloads was found**; the researchers' planning figure of 1.5 to 3 times slower is an estimate you must replace with a measurement. The current release line is Go 1.27 (19 August 2026); its SIMD packages are experimental behind `GOEXPERIMENT=simd` with an API "not yet considered stable", so leave SIMD out of the first version ([Go blog: simd experiment](https://go.dev/blog/simd-experiment)). Go 1.24 to 1.26 release notes and the Ports section of 1.27 were not read, so WASM-port changes in those releases are unknown.

The browser route has a strategic advantage: it is static files on a CDN, costs nothing to run, and never receives an untrusted upload.

### Server: dimension caps matter more than body-size caps

The main risk with untrusted images in Go is a header that declares enormous dimensions and triggers a huge allocation before pixel data is read. A 2026 report showed a **34-byte GIF causing a roughly 4 GiB allocation** in the standard library, noting that `http.MaxBytesReader` does not prevent it ([golang/go issue 79063](https://www.goodfirstissue.org/it/golang/go/issues/79063)). The documented mitigation is to call `image.DecodeConfig` first and reject oversized dimensions ([golang/go issue 27830](https://go.dev/issue/27830)). Memory arithmetic sets the cap: at 4 bytes per pixel, an 8000x8000 image is 256 MB before a label map doubles it. The fuller hardening checklist (timeouts, a concurrency semaphore, `GOMEMLIMIT`, rate limiting, first-frame-only GIF, output size caps) is standard practice that the researchers did not verify against sources.

For hosting, Cloud Run bills $0.000024 per vCPU-second with 180,000 free vCPU-seconds a month and scales to zero; its Tier 1 pricing includes the asia-south1 region ([Cloud Run pricing](https://cloud.google.com/run/pricing?hl=bg)). Computed from those rates, a one-second trace on 1 vCPU and 512 MiB costs about $25 per million. Fly.io starts at about $2.19 a month for its smallest machine but charges $0.12/GB egress in India ([Fly.io pricing](https://fly.io/pricing.md)). AWS Lambda's 6 MB synchronous payload cap makes direct image upload awkward ([Encore](https://encore.dev/articles/aws-lambda-go)). Cloud Run's request-size and timeout limits were not confirmed from Google's documentation.

### Testing: golden files, round-trip fidelity, fuzzing

Use three layers. Byte-exact golden SVGs guard against regressions and require deterministic output: fixed iteration order, fixed float formatting, deterministic merging of parallel work. A round-trip test rasterises the output and compares it with the input, reporting fidelity, path count, node count, bytes and time; VTracer ships exactly such a benchmark ([vtracer releases](https://github.com/visioncortex/vtracer/releases)). Pure-Go SVG rasterisers are thin ([oksvg](https://github.com/srwiley/oksvg) is a partial implementation last pushed in May 2023), and since the tracer emits only filled paths, a small test-only rasteriser plus an occasional cross-check against an external renderer is more trustworthy. Fuzz the decode-and-trace path with Go's native fuzzer. One trap: Go 1.27 changed `compress/flate` output, so PNG bytes can differ between Go versions; compare decoded pixels, never PNG files ([Go 1.27 release notes](https://go.googlesource.com/website/+show/refs/heads/master/_content/doc/go1.27.md)).

## A five-phase plan that ships bilevel first and goes online fourth

The ordering puts the licence-safe, lowest-risk work first and defers the two items with open legal or engineering questions (a clean-room Potrace-style fitter and seam-free cutout) until the benchmark can show whether they are worth it. The phase contents are this report's synthesis of the research, not a published plan.

| Phase | Deliverable | Contents | Exit test |

Phase 1 deliberately uses the VTracer-style and Schneider fitters for black-and-white, even though Potrace is the bilevel reference. That gets a usable tool out without touching the clean-room question, and the Phase 0 benchmark then tells you how large the quality gap to Potrace really is. If the gap is small, Phase 5's Potrace-style fitter never needs building. Shipping WASM before the HTTP API in Phase 4 follows the same logic: it is free to host, exposes no upload surface, and delivers the "offer it online" goal sooner.

## Conclusion

The licensing analysis and the engineering analysis point the same way, which is unusual and convenient: the algorithm family that is safest to reuse (VTracer's, MIT/Apache) is also the one that handles colour, runs in linear time and is under active development. The cost of avoiding Potrace code is therefore small, confined to a possible quality gap on bilevel line art that nobody has measured. That makes the in-repo benchmark the most valuable early artefact in the project: it converts the two biggest unknowns here (whether a Potrace-style fitter is worth a clean-room effort, and whether Go WASM is fast enough in a browser) from opinion into numbers.

The riskiest habit to avoid is the convenient one. Glancing at gotrace "just to check" a detail, or asking an AI assistant to port a Potrace function, would quietly undo the licence position that the whole plan depends on, and it would do so in a way that is hard to prove clean afterwards. Settle the lawyer questions in Phase 0, while the answers can still change the design for free.
